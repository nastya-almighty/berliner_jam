# Berliner Jam set list

Исходный код [berlinerjam.de](https://berlinerjam.de/): заявки на музыкальные встречи, совместные составы, распределение партий и программа джема.

**Алгоритм распределения подробно описан в отдельном [ALGORITHM.md](ALGORITHM.md).** Документ содержит объяснение для администраторов, точный порядок критериев, веса партий, примеры и ограничения текущей реализации.

## Возможности

- Общий вход по нику и паролю для участников и администраторов. `@` при входе необязателен. Роль определяется сервером по аккаунту.
- Индивидуальные и групповые заявки, основные места и резерв. Друга можно записать по нику или имени без обязательного подтверждения входом на сайт. Вокал и инструмент можно совместить конкретными партиями.
- Три уровня желания и три переносимые вокальные звезды на встречу. Звёзды выделяют предпочтения; максимум вокальных выступлений задаётся отдельно в профиле.
- Автосборка черновика программы по готовности песен, охвату людей и нагрузке на двух прошлых встречах. Основные места сохраняются; резерв подбирается на свободные партии. Предложения отмечаются голубым.
- Почти собранные песни с одной недостающей обязательной партией добавляются при наличии времени. Вне программы показываются объяснения и предложения ручных замен ради равномерного участия.
- Стоп-лист фактически сыгранных песен на две следующие встречи с серверной проверкой регистрации, переноса и утверждения.
- Кнопка «Сбросить черновик» рядом с автосборкой очищает выбор песен и предложения, сохраняя заявки, основные места и резерв.
- Ручное утверждение программы, повторное открытие, перетаскивание песен, пересчёт времени и CSV-экспорт.
- «Долгий ящик» с историей возвратов и исходной встречей. Участник видит свои записи, администратор — всю историю; доступны фильтры по исходной встрече и «Только мои».
- До 12 администраторов, приглашения организаторов, удаление и восстановление встреч и профилей.

До утверждения программы участники видят исходные заявки. После утверждения выбранные заявки отмечаются «В программе», остальные оказываются в разделе «Невыбранные заявки».

## Технологии

TypeScript, React, Vinext/Vite, Cloudflare Workers, D1 (SQLite), R2 и Drizzle. Стили находятся в `app/globals.css`; интерфейс использует компоненты и ресурсы, включённые в исходники.

Для воспроизводимого запуска используйте **Node.js 24** и **pnpm 11.25.0**. Версия pnpm закреплена в `package.json`, зависимости — в `pnpm-lock.yaml`.

## Локальный запуск

Из корня чистой копии репозитория:

```bash
pnpm install --frozen-lockfile
cp .dev.vars.example .dev.vars
pnpm build
```

В `.dev.vars` задайте собственный случайный `ADMIN_SETUP_TOKEN`. Пример содержит только заглушку. Этот файл игнорируется Git.

На **пустой локальной базе** примените SQL-миграции по порядку:

```bash
for migration in drizzle/*.sql; do
  pnpm exec wrangler d1 execute DB --local     --config dist/server/wrangler.json     --file "$migration"
done
```

Эта команда предназначена для первоначального создания локальной базы; повторное применение уже выполненных SQL-файлов может завершиться ошибкой существующих таблиц. Флаг `--local` сохраняйте: данные разработки находятся отдельно от рабочей базы.

Затем:

```bash
pnpm dev
```

Откройте адрес из вывода сервера. В переносимом окружении по умолчанию используется `http://localhost:5173`. Первоначальная настройка организатора открывается по локальному адресу `/#setup=ВАШ_ЛОКАЛЬНЫЙ_ТОКЕН`.

Для проверки утверждения в самостоятельной копии настройте `PROGRAM_APPROVERS` на auth-ID созданных локальных ведущих организаторов. Один ник не предоставляет эти права.

`scripts/install-pnpm.sh` и `scripts/install-ci.sh` содержат дополнительные настройки управляемого Linux-окружения. Для обычной чистой копии используйте команды pnpm выше.

## Проверки

Проверки чистой логики и навигации не требуют рабочей базы или секретов:

```bash
node --test tests/model.test.mjs tests/navigation.test.mjs tests/shelf.test.mjs tests/recordings.test.mjs
pnpm exec tsc --noEmit
```

Интеграционные проверки используют результат сборки:

```bash
pnpm build
node tests/api.integration.mjs
node tests/recordings.integration.mjs
node tests/security.integration.mjs
node tests/owner-recovery.integration.mjs
```

Они запускают изолированный Miniflare с временными D1/R2 и тестовыми паролями. Рабочие данные сайта не используются. Намеренная ошибка отправки тестового письма в проверке восстановления является частью сценария отказа доставки.

## Хранение данных и доступ

- Общее состояние встреч хранится в `jam_state`, изменения проверяют ревизию для защиты от одновременной перезаписи.
- Аккаунты, сессии, приглашения и токены восстановления находятся в отдельных таблицах D1. Изображения встреч хранятся в R2.
- Пароли хешируются PBKDF2-SHA-256 с индивидуальной солью; токены сессий и ссылок хранятся в виде SHA-256-хешей. Сессия использует HttpOnly-cookie со сроком 30 дней.
- Запись музыканта появляется внутри сайта; она не отправляет письмо и не требует отдельного подтверждения. Источник записи виден в полной карточке песни.
- Для почтового восстановления нужны подтверждённый адрес и настройки `RESEND_API_KEY` / `MAIL_FROM`.
- Секреты первичной настройки и приглашений передаются через окружение, а не через исходники. Одноразовое восстановление владельцем также задаётся через секретное серверное окружение.
- Сервер проверяет административные права и полномочия на утверждение. В текущем действующем проекте идентификаторы двух ведущих организаторов закреплены в `PROGRAM_APPROVERS`; это идентификаторы аккаунтов, а не пароли или токены входа.

Для самостоятельного развёртывания создайте собственный проект, D1/R2 и секреты. Идентификатор в `.openai/hosting.json` относится к действующему сайту; настройки ведущих организаторов и миграция прежнего логина в `lib/local-auth.ts` также относятся к этому экземпляру.

## Работа с изменениями

1. Обсудите изменение правил в `ALGORITHM.md`.
2. Добавьте сценарий, показывающий желаемое распределение, в `tests/recordings.test.mjs`, `tests/model.test.mjs` или `tests/shelf.test.mjs`.
3. Измените реализацию, запустите подходящие проверки и проверьте интерфейс при изменении форм.
4. Публикуйте после проверки организатором. Изменение алгоритма само по себе не утверждает рабочую программу встречи.

Применённые SQL-миграции сохраняйте; для изменения схемы создавайте новые. Сторонние лицензии, включённые в проект, находятся в `vendor/` и рядом с соответствующими файлами.
